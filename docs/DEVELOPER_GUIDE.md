# Developer guide

This guide is for a developer who did not build the site and now has to maintain or extend it. It explains how the
pages run, how they are put together, what every file in `site/` does, where to make common changes, the coding
conventions the code follows, and how a change is checked.

Related records:

- `docs/DELIBERATE_DIFFERENCES.md`: every place where the site does something other than CVI's own app on purpose,
  and why. Read it before "fixing" something that looks unlike CVI.
- `site/PROVENANCE.md`: where every bundled data file, font, icon, logo and library comes from, and its license.
- `tests/README.md`: the test suites and the full regression chain.
- `docs/FUTURE_ENHANCEMENTS.md`: planned work that is not built yet.

## 1. What the site is and how it runs

The site is a set of static web pages in `site/`. There is no build step, no package manager and no server-side
code. A browser opens the files directly.

- `site/index.html` is the landing page. The user chooses files, a folder or a ZIP, sees a data checklist, and opens
  a dashboard.
- `site/cvi/index.html` is the CVI Traceability dashboard (WA State, County Focus and National Flow maps, charts,
  exports, Premise Lookup).
- `site/infrastructure/index.html` is the Infrastructure dashboard (facility layers, with optional CVI activity).

To run it, open `site/index.html` in Chrome or Safari (double-click, or File, Open). To host it, serve the `site/`
folder as it is from any static web server. Letter case in paths matters on most servers, so keep file names exactly
as they are referenced. A hosted copy should have an origin of its own, not one shared with unrelated pages (see the
hand-off notes in `site/shared/load.js`).

The user's files are read in the browser with the File and Blob APIs. Nothing is uploaded, and no data file is stored
in the site. The sample bundles are generated by code (`site/cvi/sample.js`, `site/infrastructure/sample.js`,
`site/shared/sample.js`) and contain only made-up values.

### Content Security Policy and network use

Each page sets a Content Security Policy in a `<meta http-equiv="Content-Security-Policy">` tag near the top of its
`<head>`. The important parts:

| Directive | Landing page | CVI and Infrastructure pages | Consequence for the code |
|---|---|---|---|
| `script-src` | `'self' file:` | `'self' file:` | No inline `<script>` blocks and no `onclick=` attributes. Every script is a file. |
| `img-src` | `data: blob:` | `data: blob:` | Pictures must be `data:` or `blob:` addresses. This is why the logo and the tab icon are base64 in `site/shared/brand.js`. |
| `connect-src` | `'none'` | the tile hosts only | The only network requests the site can make are opt-in tile basemaps. |
| `worker-src` | none | `blob:` | MapLibre runs its workers from `blob:` addresses. |

The offline county map is the default and fetches nothing. A tile basemap is fetched only when the user picks one.
The list of basemaps and their hosts is in `site/cvi/app/basemaps.js` (`allowed()` is the gate that `map.js`
applies to every request MapLibre makes). The CSP's `connect-src` on the CVI and Infrastructure pages is the outer
limit and must list the same hosts. A basemap marked `publish: false` (CARTO, Esri) has terms that cover WSDA's own
pages only; a copy for another host leaves it out (section 4, "A public copy"). The branded PNG tile backgrounds come from Esri's `server.arcgisonline.com`, through
`site/shared/tiles.js`, with the live map's request rules (no redirect, no credentials, no referrer); they follow
the Esri basemaps, so a copy without Esri's terms removes them from the pickers too
(`site/PROVENANCE.md`).

## 2. How the pages are put together

### Script load order

Each page loads plain script files with `<script src>` tags at the end of its `<body>`, in a fixed order. Read the
tags at the end of `site/index.html`, `site/cvi/index.html` and `site/infrastructure/index.html` to see it. The
rules that order follows:

- Data globals and libraries before the modules that use them: `../vendor/maplibre-gl/maplibre-gl.js`,
  `../geo/wa-counties.js`, `../geo/regions/index.js` (on the Infrastructure page the loader modules come first, which
  is fine because none of them uses these while loading).
- Pure modules next. Most modules reach the modules they need through small getters such as
  `const S = () => root.CVIWA.scaling;`, so the order between them matters only when a module uses another while it
  is loading.
- A few real dependencies: `cvi/app/icons.js` before `shared/brand.js` (button icons); `shared/zip.js` before
  `shared/load.js`; `shared/facility-datasets.js` before `cvi/datasets.js`, and `cvi/datasets.js` before
  `infrastructure/datasets.js` (Infrastructure reuses the CVI master's description); `shared/branded.js` before
  `cvi/app/brandedmaps.js`; `cvi/app/lookup.js` before `cvi/app/ui.js`; `shared/release.js` first on the CVI and
  Infrastructure pages (`basemaps.js` and `tiles.js` read it as they load).
- The page's wiring file last: `landing.js`, `cvi/app/ui.js` or `infrastructure/app.js`. It reads the page's
  elements and starts everything when it loads.

### Namespaces and data globals

Every module adds itself to one of two global objects:

| Global | Holds | Example |
|---|---|---|
| `window.CVIWA` | the CVI page's modules (`site/cvi/app/*.js`), some also used by Infrastructure | `CVIWA.scaling`, `CVIWA.map`, `CVIWA.brandedmaps` |
| `window.WSDA` | shared modules (`site/shared/*.js`), the dataset lists and the page objects | `WSDA.load`, `WSDA.checklist`, `WSDA.profiles.cvi`, `WSDA.landing` |

`shared/facilities.js` is published under both names (`CVIWA.facilities` and `WSDA.facilities`).

The generated data files in `site/geo/` each set one global: `window.CVIWA_GEO` (Washington's counties),
`WSDA_US_STATES`, `WSDA_STATE_CENTERS`, `WSDA_US_INSETS`, `WSDA_STREETS`, `WSDA_CITYLIMITS`, `WSDA_PLACES`,
`WSDA_TRACTS`, `WSDA_REGIONS` (the region list) and `WSDA_REGION_DATA` (one entry per loaded region).

### Files loaded later, on demand

Large files are loaded only when they are first needed, by adding a `<script>` tag from the site folder (this works
over `file://` and `http`, and keeps the CSP unchanged):

| What | Loaded by | When |
|---|---|---|
| `geo/us-states.js`, `geo/state-centers.js`, `geo/us-insets.js`, `cvi/app/flowmap.js` | `FLOW_FILES` and `loadScript()` in `cvi/app/ui.js` | the National Flow view is first chosen |
| `cvi/app/focusmap.js` | `FOCUS_FILES` in `cvi/app/ui.js` | the County Focus view is first chosen |
| `cvi/app/lookupmap.js` | `cvi/app/lookup.js` (through the page's `loadScript`) | the first Premise Lookup result |
| `geo/streets-wa.js` | `cvi/app/ui.js` and `cvi/app/lookup.js` | the "Streets (vector)" PNG background is first used |
| `geo/citylimits-wa.js`, `geo/places-wa.js`, `geo/tracts-wa.js` | `WSDA.population.load()` (`shared/population.js`) | a population layer is first switched on (`tracts-wa.js` also when Emergency Response's Overview first works out the people inside the zones) |
| `geo/regions/<id>.js` | `WSDA.regions.load()` (`shared/regions.js`) | a neighboring region is first switched on |
| `geo/wa-counties.js` on the landing page | `needGeo()` in `landing.js` | the all-in-one sample is first downloaded |

### The path of a file, from the drop area to a map

1. **Intake** (`site/shared/load.js`). The landing page's file picker, folder picker and drop area (`#drop`) call
   `WSDA.load.fromFileList()` or `WSDA.load.fromDataTransfer()`. These turn the selection into one flat list of items,
   unpack ZIP files with `site/shared/zip.js`, skip system clutter and report problems in plain words. Each item has
   `read()`, `text()` and `head(n)`.
2. **Recognition** (`site/shared/recognize.js` with a profile's dataset list). `WSDA.recognize.recognize(items,
   profile, opts)` decides which file is which dataset, from header rows only. The dataset lists are
   `site/cvi/datasets.js` (`WSDA.profiles.cvi`) and `site/infrastructure/datasets.js`
   (`WSDA.profiles.infrastructure`). A `bundle.json`, if present, is read by `site/shared/bundle.js` and ranks the
   claims (the user's pick, then `bundle.json`, then columns and names).
3. **Checklist and feature gating** (`site/shared/checklist.js`). `checklist.create(...)` builds the panel;
   `show(loadResult)` runs recognition and shows datasets found and missing, the features each one turns on, and the
   reason for anything that is off. `gate(result, profile)` is the pure rule; `applyGates(scope, features)` grays the
   page elements marked `data-feature="<feature id>"`.
4. **Hand-off to a dashboard tab** (`WSDA.load.handoff` in `site/shared/load.js`). The landing page calls
   `handoff.open(profileId, url, build, onStatus)`, which opens the dashboard in a tab named `wsda-<profile>` with a
   random key in its address. The dashboard calls `handoff.receive(profileId, onFiles)` and gets the files in memory
   through a private `MessageChannel`. Nothing is written to disk. Which datasets are sent is decided by `payloadFor()`
   in `landing.js`: the datasets the profile's features need, plus every found dataset whose kind is in its
   `handoffKinds`.
5. **On the CVI page** (`site/cvi/app/ui.js`). `handoff.receive('cvi', ...)` passes the master file to `loadFile()`,
   the same path as choosing a file on the page. Then:
   - `cvi/app/csv.js` parses the CSV and `cvi/app/master.js` (`master.load()`) checks the 13 required columns and
     normalizes the rows as CVI's `load_master_csv()` does.
   - `gateControls()` in `ui.js` applies the feature gates to the page.
   - `recompute()` (debounced 250 ms) filters and aggregates: `cvi/app/aggregate.js` (`aggregate.build()`) makes the
     WA State circles, `summary.js` the value boxes and strip, `scaling.js` the radii and legend tiers.
   - `cvi/app/map.js` (`map.draw()`) draws the WA State map. National Flow uses `flow.js` (rules) and `flowmap.js`
     (drawing); County Focus uses `focus.js` and `focusmap.js`.
   - `ui.js` keeps all control state (the objects `st` for WA State, `fl` for National Flow, `fo` for County Focus)
     and redraws the legend, boxes, charts and exports.
6. **On the Infrastructure page** (`site/infrastructure/app.js`). Files arrive by the same hand-off or by the page's
   own picker (the same `load.js`, `recognize.js` and `checklist.js`). `facilities.prepare()`, `select()` and
   `reconcile()` turn facility files into layers; `shared/facilitymap.js` draws them through `CVIWA.map` (as a map
   "kind"); an optional master adds CVI activity circles through `master.js` and `aggregate.js`.

"Pure" means the module does not touch the page or the map: it takes data and returns data, and the Node unit tests
load it directly. "Page" means it reads or writes page elements or a MapLibre map. "Mixed" means a pure core with a
small page part (named in the line). "Data" means it only holds values.

### Vendored library (`site/vendor/`)

`site/vendor/maplibre-gl/` holds MapLibre GL JS 5.22.0 (`maplibre-gl.js`, `maplibre-gl.css`, `LICENSE.txt`), copied

## 4. Where to change what

Before changing a rule, read the header comment of the file: it says which CVI function the rule follows, or why it
differs from CVI. Many rules are checked against CVI's own R functions by the tests.

### A palette or a brand color

- **Map direction palettes (WA State circles, Infrastructure activity):** `DIRECTION_PALETTES` in
  `site/cvi/app/palettes.js`. The pickers are filled from its keys (`ui.js` and `infrastructure/app.js`), so a new
  entry appears without other changes. `circleColor()` gives the Combined color (the palette's first color).
- **National Flow species palettes:** `SPECIES_PALETTES` in the same file.
- A color that differs from CVI's must be added to `CVI_VALUES` with CVI's value; the tests compare the rest with CVI.
- Default circle and chart colors also appear in `COLORS` in `site/cvi/app/aggregate.js` and

### Adding an emergency type

The Emergency Response dashboard names no emergency in its code: each emergency is one small file in
`site/emergency/types/` that the page reads. HPAI (`types/hpai.js`) is the first and New World screwworm
(`types/nws.js`, zones from a dispersal-area file) the second; a test-only made-up type
(`tests/synthetic/em_made_up_type.js`) shows that a third one needs no other change.

1. **Copy `site/emergency/types/hpai.js`** to `site/emergency/types/<your-id>.js` and change its fields. Its top
   comment explains each one:
   - `id` (lowercase letters, digits, dashes), `name` (as shown on the page) and `title` (the map picture's title,
     for example "HPAI RESPONSE MAP"; left out, the name in capitals with "RESPONSE MAP");
   - `diseaseWords`: words in a positives file's disease column (`columns.disease`) that pick this type (any case; a
     word matches at the start of a word, so "h5" matches "H5N1"). A file with no disease column gets the first type
     loaded;
   - `columns`: the column names the page reads for each role, any case, the first name the file has winning: `id`
     (the positive's name), `detected` (the detection date, in order of preference; a row whose first date is blank
     takes the next), `disease`, `status`, `quarantine` (the quarantine release date), `flockType` (Commercial,
     Backyard; counted in the Overview's animals box), `inventory` (the number of animals, thousands commas
     allowed; added up in that box and giving the flock size class) and `shown` (further columns for the hover and
     the export). A renamed column in the agency's table is one edit here. A name holding address, location, street
     or premise is refused: those columns are never read;
   - `inventoryWord`: the word after the animals' total in the Overview's animals box ("4.1M birds"; "animals" when left out);
   - `countedApart`: animals added up apart from `inventoryWord`, each entry's species words and the word they are
     counted under (HPAI: "3,550 cattle, 45 other animals"); a positive counts under the first entry with a word in
     its species;
   - `statuses`: each status's label, the spellings a file may use for it, and its map color (`#rrggbb`);
   - `closed`: `column` (the column or columns that mark a positive closed), `values` (the values that do) and
     `dateColumn` (the date surveillance ended, when the file has one). A positive is past on the window's end date
     when its closed date is on or before it, or, without a readable closed date, when its closed column says so; a
     past positive never gets zones or counts;
   - `zones`: `source` ("rings" around each positive, or "file": zones come from a zone file, which then replaces the
     rings as soon as it is loaded), `rings` (each ring's distance, label and color), `applyTo` ("open": positives
     not closed; "confirmed": the first status only; "all" is refused with its reason, since past positives never get
     zones) and `unit` ("km" or "mi", the unit of the ring distances; the page's km | miles switch converts both
     ways);
   - `layers`: the facility layers suggested for checking, by their keys (the built-in layer ids, or the `key` column
     of the facility layer list, the manifest): `bySpecies` maps words in a positives file's species column to keys,
     `default` is used when no word matches. A suggested layer whose file is not loaded is skipped;
   - `links`: reference pages (label and an `https://` address), shown behind the type's "?" and opened in a new tab.
   If none of the type's column names is one of the positives file's marker columns (`MARKERS` in
   `site/emergency/datasets.js`: Case ID, Confirmed Diagnosis, Close Date, Subtype, and the earlier forms), add one of
   them there, so the landing page and the Emergency page recognize its file.
2. **Add one script line** for it in `site/emergency/index.html`, after the last `types/` line:
   `<script src="types/<your-id>.js"></script>`. The order of the lines is the order of the type picker; the first
   type is the default.
3. **Run the unit suite:** `node tests/node/run_em_unit_tests.js`. `types.js` checks every field when the page loads
   and names any field that is missing or of the wrong form (for example `Emergency type "nws": "zones.rings[0].distance"
   should be a number above 0, at most 500`). To test your type the way the made-up one is tested, load its file in
   the suite after `hpai.js` and check that its words pick it, its statuses and closed values reach the positives, and
   its layer keys are suggested (section 1, "The third-type test", and section 8 of the suite).

**What a type cannot express yet.** Positives are points (a latitude and a longitude each). An emergency whose
detections are whole counties, with no coordinates, is the first known case the template does not cover; zones by
county would be the way to add it (`site/shared/facilities.js` `countyMembership` already tests points against
county polygons).

## 5. Coding conventions

The code follows these conventions. Keep to them in new code.

- **Plain JavaScript, ES2017 or newer, no packages and no build step.** Each file is one immediately invoked
  function: `(function (root) { 'use strict'; ... })(typeof window !== 'undefined' ? window : globalThis);`.
  Passing `globalThis` lets the same file load in Node for the unit tests.
- **Exports on the namespace at the end of the file**, for example `root.CVIWA.palettes = { ... };` or
  `root.WSDA.checklist = { ... };`. Constants a test checks are exported too.
- **Pure where possible.** Rules (counting, classes, colors, layout) live in pure modules; page files only wire
  controls and draw. New rules belong in a pure module so a Node test can check them.
- **A header comment in every file.** It says what the file does, which CVI function it follows (by file and
  function, often with line numbers in CVI's R code), and why a rule differs from CVI where it does (the difference
  is also listed in `docs/DELIBERATE_DIFFERENCES.md`). Keep it up to date when a rule changes.
- **Comments over non-obvious functions,** saying what goes in and what comes out, and why when the reason is not
  plain. Long files are divided by section comments (`// ── Name ──` or `// ---- name ----`).
- **Line length:** most lines are under 120 characters. Generated data and base64 lines are the exception.
- **American spelling** in code, comments and page text. Quotes and proper names stay as written.
- **No network.** No fetch, no CDN, no web font, no analytics. The only exception is the opt-in basemaps and PNG
  tile backgrounds, behind the request gate and the CSP. Pictures are `data:` or `blob:`.
- **User text is never trusted.** Text from the user's files reaches the page through `textContent` and text nodes,
  or through an escaping helper before it becomes HTML or SVG: `esc` in `shared/checklist.js`, `shared/guide.js`,
  `shared/branded.js` (which also removes control and direction characters), `cvi/app/focus.js`,
  `cvi/app/chartsvg.js`, `cvi/app/map.js` and `cvi/app/lookupmap.js`. Ids built from user values are avoided
  (`facility-ui.js` builds ids from list positions). Objects keyed by user values are made with
  `Object.create(null)`.
- **Deterministic output.** Samples and exports use no clock or random numbers unless a date is part of the export.
  Sorting follows the order CVI's R code uses (`collate` for R's `sort()`, `cmpC` for the C locale).

## 7. Known layout note: the CVI page's fixed banner height

Left as it is for now; noted here for a later fix.

The CVI page sizes its layout by subtracting a fixed banner height from the window height. `--banner-height: 50px`
is set in `site/shared/brand.css`, and `site/cvi/index.html` uses it in `.layout { min-height: calc(100vh -
var(--banner-height)); }` and in the sidebar's `max-height: calc(100vh - var(--banner-height))`.

The banner can be taller than 50 px: it wraps below about 900 px of window width or with larger text, and the
`#bundle-banner` line shows under it when the files came with a `bundle.json` banner. Then the sidebar ends 25 to
40 px below the bottom of the window, and its last controls need a page scroll.

A later fix could be either of these:

- Make the page a column flex layout (banner, bundle line, then `.layout` with `flex: 1` and `min-height: 0`), so
  the layout takes whatever height is left and no fixed number is needed.
- Measure the banner and the bundle line with a `ResizeObserver` and write their height into `--banner-height`.

Either fix changes the page's layout, so it needs before-and-after screenshots at several window sizes.

## 8. How a change is checked

The suites, how to run them and the full regression chain are described in `tests/README.md`. In short: Node unit
suites (`tests/node/`) check the pure modules, many against CVI's own R functions run on the same synthetic files
(`tests/oracle/`); browser suites (`tests/browser/`) drive the pages in Chrome, plus a Safari run; mutation runs
(`tests/mutation/`) check that the tests catch deliberate mistakes. Run the full chain before a release and after
any change to shared code, the geo files or the vendored library. The tests use synthetic data only.

Two more rules apply to every change that a person can see:

- **Every visible change is compared before and after:** screenshots of the page or the export before the change
  and after it, side by side, for review before the change is accepted.
- **Every new feature gets numbered manual test steps before release:** a short list of numbered steps that a person
  follows in the browser, one behavior per step, each with the result to expect, recorded with its outcome.

Record a new deliberate difference from CVI at the top of the second section of `docs/DELIBERATE_DIFFERENCES.md`, and
any new bundled source in `site/PROVENANCE.md`.

### Raising the version

Every published update is a version. `VERSION.txt` at the top of the repository holds it on one line, the number and
the date of publishing (`1.0 2026-10-20`), and each page's footer line ends with the same, written into the HTML
(`<span class="version">Version 1.0 (2026-10-20)</span>` in `site/index.html`, `site/cvi/index.html`,
`site/infrastructure/index.html` and `site/emergency/index.html`), so it shows even when a script is blocked. A small
update raises the second number (1.1, 1.2 ...); a new dashboard raises the first (2.0). Change the five places
together: the UI unit suite
(`tests/node/run_ui_unit_tests.js`) fails when a footer and `VERSION.txt` differ.

## 9. Decisions a maintainer needs

These decisions shape the code and the release. Keep to them unless the agency decides otherwise.

- **Synthetic data only, until the agency approves real data.** Development, tests, samples and pictures use made-up
  data, and no operational data is committed. Real data reaches users only as the files they are given and load in
  the page: the files are read in the browser and passed between tabs in memory, never uploaded or stored. The site
  has no password; if possession of the files is ever not enough, the answer is an encrypted bundle the page unlocks
  in the browser, as a piece of work of its own.
- **The data decide what each person sees.** Everyone opens the same pages. A missing dataset, column or supporting
  file turns off only the features that need it, with a plain reason, and never breaks the page. The page has no
  access presets; who receives which data is decided outside the app.
- **Offline by default.** The maps are drawn from bundled outlines. Tile basemaps and PNG tile backgrounds are opt-in,
  fetched only when picked and only from their provider's hosts, behind the request gate and the CSP (section 1);
  redirects are refused and the credit is shown. National Flow and Premise Lookup's address lookup are offline only,
  and the tests make no network requests. A network address lookup, if ever added, would be the Census geocoder only,
  opt-in and with a notice, and needs the agency's decision.
- **Providers cleared for WSDA's pages only.** CARTO (six basemaps) and Esri (six basemaps and the three PNG tile
  backgrounds) are cleared for WSDA's own pages; a copy for another host leaves them out with the public-copy switch
  (section 4, "A public copy"). WSDOT and the WA Department of Revenue city limits are cleared for any copy.
- **Parity with CVI.** CVI's app is the reference and is never changed; the tests compare the pages with CVI's own R
  functions. Branded PNGs and GIFs follow CVI at structural parity (the same elements, values, colors and layout
  regions), not pixel for pixel. Every deliberate difference is listed in `docs/DELIBERATE_DIFFERENCES.md`; a new one
  needs approval and an entry there. Location precision and agricultural coverage wait for CVI to settle them.
- **Brand and accessibility.** WSDA-named palettes use the brand guide's exact colors; other CVI palettes are
  unchanged. Open Sans is bundled; text keeps to 0.85rem for body text and 0.75rem for notes and tables. Page text
  meets 4.5:1 contrast; on the PNGs and GIFs, text under 11 pt is only black or white. Facility layers get a shape as
  well as a color. The logo and tab icon are approved for WSDA's pages, a public demo copy included.
- **Conventions.** American spelling in all new text (quotes and proper names as written); readable code in the
  surrounding style (section 5); no new library or install without approval.
- **Release wording.** The banner's "SYNTHETIC DATA ONLY" badge and the footer line "Synthetic test data only. Not an
  official WSDA service." come off only when the agency approves real data, with nothing in their place.
- **Changes after release.** A change to shared code that another dashboard reuses (facility layers, loading,
  buffers) runs every affected dashboard's full regression chain and adds a version note (`bundle.json` "release").
